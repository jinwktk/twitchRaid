1. プログラム概要

このBotは Twitch チャンネル rukalun のチャット、配信開始/終了、 Raid、Clipを見張る常駐プログラムです。現行の運用対象はTypeScript版だけです。 Python版のファイルは過去資産とテスト互換のため残っていますが、仕様書とGitHub Pagesは TypeScript版へ一本化しています。

1

Twitchを見る

Twurpleの ChatClient と Helix API で、チャット、配信状態、 Clip、VOD、Raidを取得します。

2

Botが考える

src/bot.ts が中心になり、コマンド処理、クールダウン、状態保存、 再接続、トークン更新を進めます。

3

Discordへ届ける

配信開始は @everyone とEmbedカードで知らせます。 配信まとめ、Clip URLもDiscordへ投稿し、可能なら開始通知からまとめスレッドを作ります。

2. 全体マップ

Botは「駅の案内係」のように、Twitchから届く出来事を受け取り、必要な箱へしまい、 必要な場所へ知らせます。

3. 機能一覧

ここでは「人がチャットで呼ぶ機能」と「Botが自動で動く機能」に分けて見ます。

基本コマンド

  • !help: 主要コマンド一覧（文頭!で読み上げ回避）
  • !age: 年齢を返す
  • !goods: BOOTH URL
  • !weight / !height
  • !mood / !menu

Clipコマンド

  • !clip: ランダムClip
  • !myclip: 自分作成Clip
  • !clipsearch <キーワード>: タイトル/作成者名検索
  • !clip / !myclip はSQLite優先、APIはフォールバック
  • !clipsearch はSQLiteキャッシュ検索のみ
  • 通常ユーザーは30分クールダウン

管理系コマンド

  • !mangaon / !mangaoff
  • !shoutout <name>
  • !streamnotify
  • broadcaster / mod / 管理者リストで判定

統計コマンド

  • !speed: 直近60秒の風速
  • !commentcount: 配信中コメント数
  • !boom: 過去30日ゲーム時間
  • GraphQL結果は5分キャッシュ
自動機能 何をするか 保存/出力
配信開始通知 180秒ごとにライブ状態を確認し、@everyone とEmbedでタイトル、ゲーム、視聴者数、配信プレビュー、Twitch URLをDiscordへ送る。 LAST_STREAM_TITLE、startMessageId、threadId
配信まとめ 配信中のコメント数、Raid数、ClipをJSONへ保存し、終了時にまとめる。 data/stream-summary-state.json、Discordスレッド
Clip同期 起動時バックフィル、1分ごとの直近同期、オフライン時の日次再走査を行う。 data/clips.sqlite、削除/非公開Clipの無効化
Raid対応 Raid元のURL、タイトル、ゲームを取得し、Ollamaまたは固定文で1通のRaid挨拶文を出して、shoutoutをキューに入れる。 Twitchチャット、Twitch shoutout API、Ollama API
自動復旧 切断時の再接続、2時間ごとのtoken refresh、Git更新後build、PM2再起動。 logs/bot_YYYY-MM-DD.log、last_restart.txt

4. 処理フロー

重要な流れを「一本道」にしました。左から右、または上から下へ進みます。

4.1 起動フロー

1

設定を読む

Config が .env を読み込む。

2

Git確認

更新があれば git pull と npm run build。

3

Token確認

Twitch tokenをvalidateし、必要ならrefresh。

4

接続準備

Twurple API、ChatClient、SQLite同期器を作る。

5

監視開始

keep-alive、配信監視、Clip同期を開始。

4.2 配信開始から終了まとめまで

!streamnotify の特別ルール

配信開始通知が漏れた時、管理者が !streamnotify を実行すると、 タイトル重複スキップを通さずDiscordへ開始通知を送ります。 その新しい投稿の startMessageId と threadId を既存stateより優先します。

古いスレッドを使わないルール

新しい開始通知が作られたのに threadId が返らない場合は、 古い threadId を残しません。これで別配信のスレッドへClipを送る事故を防ぎます。

開始通知を2通にしないルール

通常の開始通知を送った直後にスレッド作成だけ失敗しても、同じ開始処理内では 開始通知を投稿し直しません。Clipや終了まとめを投稿する前の保証処理でも、 保存済みの開始通知からスレッド作成だけを再試行し、新しい開始通知は自動投稿しません。 再送したい時は !streamnotify で明示的に送ります。

4.3 Raid対応フロー

1

Raid検知

onRaid でRaid元と人数を受け取る。

2

情報取得

Raid元のURL、タイトル、ゲーム名をTwitch APIで取得。

3

キュー投入

ShoutoutQueue に対象を入れる。

4

挨拶文作成

Ollamaが有効ならRaid挨拶文を生成。採用/失敗理由はログへ残し、失敗時は固定文へ戻る。

5

1通だけ投稿

AI文または固定文のどちらか1通だけをチャットへ送る。

6

429なら待つ

レート制限時は同じ対象を先頭へ戻し2分後に再実行。

src/commands/shoutout.ts 手動/自動shoutout、対象名正規化、権限判定、429時再キュー。
src/commands/shoutout-introduction.ts Ollama /api/generate でRaid挨拶文を作り、Twitchチャット向けに単一行・250文字以内へ整形。URLは残し、絵文字は除去。Raid人数はAI入力に含めず、低人数を下げる表現は採用しない。AI文がゲーム名や配信タイトルを落とした場合は不足分だけを補って採用する。タイトル主要部が既に含まれていれば、長い 配信では... 定型文は追記しない。採用/フォールバック理由もログ化する。

src/git-manager.ts / src/system-watcher.ts 10分ごとのGit更新確認、pull後build、即時PM2再起動、24時間間隔の定期再起動。

6. 保存するデータ

配信まとめstate

再起動しても配信まとめを失わないよう、配信中の状態をJSONで保存します。 

{
  "status": "active",
  "streamId": "316055131251",
  "title": "配信タイトル",
  "gameName": "ゲーム名",
  "startedAt": "2026-06-06T01:05:28.000Z",
  "startMessageId": "1512655504424570990",
  "threadId": "1512655504424570990",
  "commentCount": 123,
  "raidCount": 1,
  "postedClipIds": []
}

Clip SQLite

data/clips.sqlite にはClip本体、サムネイルURL、ゲームID/ゲーム名、表示履歴、走査済み期間、 同期時刻、削除/非公開化されたClipの unavailable_at を保存します。

  • clip_cache: Clip情報と有効/無効状態
  • clip_history: !clip / !myclip:user / !clipsearch:query ごとの表示履歴
  • clip_scan_windows: 全期間バックフィルの完了窓
  • clip_sync_state: 直近同期と日次再走査の時刻
  • 直近同期では一覧から消えたDB既存Clipを getClipsByIds で確認し、返らないClipだけ unavailable_at を設定
  • !clipsearch がClip件数増加で遅くなった場合はFTS5または検索専用テーブルへの移行を検討

GitHub Pages Clip検索データ

docs/clip-search-data.json は data/clips.sqlite から生成する公開用データです。 Clip検索画面 docs/clip-search.html が読み込みます。

  • 公開項目は id、URL、タイトル、作成者表示名、ゲーム名、サムネイルURL、作成日、再生数、clipSync.recentSyncedAt のみ
  • unavailable_at があるClipは除外
  • Clip最終同期時刻は clip_sync_state.recent_sync_at を元にJSTの秒単位で表示
  • 各カードにサムネイルとゲーム名を表示し、再生は Twitchで見る 外部リンクだけにする
  • creator_id、ゲームID、表示履歴、その他の内部state、認証情報は公開しない
  • 更新は npm run docs:export-clips で行い、必要時は --enrich-from-twitch でTwitch API補完する

7. 失敗時の守り方

外部APIは失敗します。だから、失敗してもBot全体が止まらない道を用意しています。

場面 守り方 注意点
Discord Bot APIが403などで失敗 DISCORD_WEBHOOK_URL があればWebhook投稿へフォールバック。 Webhook fallbackは本文欠落防止。メッセージ起点スレッド作成はBot権限に依存。
threadId が無い 保存済み startMessageId からスレッド作成を再試行。 保存済み開始通知が無い、またはスレッド作成に失敗した場合も自動再投稿しない。必要なら !streamnotify で手動再送する。
開始通知は新しいがスレッドが無い 古い threadId を明示的に消す。 別配信のスレッドへ投稿済み扱いで進む事故を防ぐ。
Raid shoutoutが429 対象をキュー先頭へ戻し、2分後に同じ対象を再実行。 429時はtoken refreshによる即時リトライをしない。
Raid元の配信情報が取れない タイトル/ゲームなしでもチャンネルURL付きフォールバック文を送る。 Raid直後は元配信が既にオフラインのことがある。
Ollama挨拶文が生成できない 固定Raid挨拶文へフォールバックし、Twitch shoutout APIは継続。AI生成文はコード側で250文字以内に丸め、`人数少なかった` などの表現は採用しない。ゲーム名/配信タイトルが抜けた場合は不足分だけコード側で補う。 OLLAMA_SHOUTOUT_ENABLED=true と OLLAMA_SHOUTOUT_MODEL 設定時だけ有効。既定は timeout=15000ms / keep_alive=30m。採用/フォールバック理由はログで確認できる。
ClipがTwitch APIから消えた 直近同期で一覧から消えたDB既存Clipを getClipsByIds で確認し、返らない場合は unavailable_at を入れて候補から外す。日次再走査も同じ無効化を補完する。 APIに再登場したClipは自動で有効化される。通常バックフィルと競合して日次再走査が未完了だった場合は daily_reconcile_at を更新しない。
チャット接続が切れた 最大10回まで遅延再接続し、上限到達時はプロセス再起動。 遅延は15秒から最大60秒。
token validateが401 refresh token APIで更新し、成功したら .env を安全更新。 validate結果は5分TTLでキャッシュし、API負荷を下げる。

8. パフォーマンス・運用メモ

APIを呼びすぎない工夫

  • ClipはSQLiteキャッシュ優先。
  • 直近Clip同期は1分ごとに既定6時間分を取り直す。
  • 全期間再走査は配信していない時に1日1回。
  • token validateは5分TTLキャッシュ。
  • 配信まとめのコメント数JSON保存は30秒デバウンス。

重い処理の抑制

  • !boom はVODを最大4本並列で処理。
  • !boom 結果は5分メモリキャッシュ。
  • Clip全期間走査は30日窓に分割し、多すぎる窓は再分割。

運用で見るログ

  • 直近clip同期完了: fetched=..., saved=..., unavailable=..., windowMinutes=...
  • 配信まとめスレッドへ新規クリップを投稿しました
  • Discord bot message failed: 403
  • Shoutout rate limited
サブPC確認ルール: Botは主にサブPCで稼働します。通知やClipの問題調査では、ローカル作業PCだけでなく、 サブPC側のPM2ログ、logs/bot_YYYY-MM-DD.log、data/clips.sqlite、 data/stream-summary-state.json を確認します。
